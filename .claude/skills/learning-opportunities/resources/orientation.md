# Repo Orientation: agent-template

> Generated by orient. Re-run to update.

## One-line purpose
A course-provided configuration of AI coding agents, skills, hooks, and templates for CS3704 at Virginia Tech. It gives students guided, policy-bound agentic development (assignment intake, learning goals, quizzes, requirements and design help, submission packaging) rather than a general-purpose assistant.

## Primary language(s)
- Markdown (agent and skill definitions, templates, docs). This is the dominant "code" in the repo.
- Bash/POSIX sh (`.claude/scripts/*.sh`, `hooks/*`, `setup.sh`)
- TypeScript (one opencode plugin: `.claude/plugins/learning-opportunity.ts`)
- JSON/YAML config (`opencode.json`, `baker.yml`, `.claude/topics/concept-lecture-map.json`)

No language manifest (package.json, pyproject.toml, etc.) exists. Dependencies are installed by `baker` from `baker.yml`.

## Pipeline / workflow stages
The student workflow for each assignment:
1. **Bake**: `baker bake .` installs opencode and the git pre-commit hook (`baker.yml`). `baker run setup` prints the next steps.
2. **Analyze**: `@assignment analyze HW1` resolves the source (`scripts/assign-source.sh`) and writes `HW1.md` at the root from `docs/templates/assignment.md`.
3. **Set goals**: `/learning-goal` writes `learning-goal.md` / `team-goal.md` / the semester goal and logs to `learning-log.jsonl`.
4. **Work**: the primary agents (`plan`, `build`) and the phase-gated subagents (`requirements-analyst`, `system-architect`, and others) produce artifacts from `docs/templates/`.
5. **Learn along the way**: commits trigger learning-opportunity nudges through the plugin or hooks. `quiz` and `concept-explain` run concept checks, and quizzes are logged to `teacher-log.jsonl`.
6. **Submit**: `@assignment submit` runs `scripts/submit-package.sh` (or `submit-link.sh` / `submit-file.sh`) to build a Canvas-ready package.

## Key files
- `AGENTS.md`: the shared policy every agent obeys (identity, quiz budget, logging, delegation table, agent contract) | read it first, since every agent file defers to it
- `PHASE.md`: lists which agents and skills are live this semester phase | explains why some agents "exist" but should not be invoked yet
- `.claude/agents/assignment.md`: the analyze → verify → submit subagent | the backbone of every assignment's lifecycle
- `.claude/agents/build.md`: the primary editing agent, which also owns semester-goal writes | shows how permissions in frontmatter define an agent's role
- `.claude/skills/quiz/SKILL.md`: course reference, learning outcomes L1–L7, quiz budget, and `teacher-log.jsonl` schema | the authoritative source for outcome IDs and quiz logging
- `.claude/skills/learning-opportunities/SKILL.md`: post-work learning exercises | the target of all the commit hooks
- `.claude/plugins/learning-opportunity.ts`: opencode `tool.execute.after` plugin that nudges after `git commit` | the active in-opencode trigger mechanism
- `hooks/post-commit` + `.claude/scripts/post-tool-use.sh`: commit-triggered nudges outside opencode and the legacy hook path | show the shared `/tmp/lo_auto_*.state` rate limiting
- `docs/templates/`: assignment, use-case, user-story, diagram, data-model, and ADR templates | what the phase-2 agents produce
- `opencode.json` / `baker.yml`: model provider (VT ARC) and environment install | where setup problems usually come from

## Core concepts
**Agent vs. skill**: An *agent* (`.claude/agents/*.md`) is a role with a permission block (what it may read, edit, or run). A *skill* (`.claude/skills/*/SKILL.md`) is a reusable procedure that any agent can load. Agents delegate to each other with `Task()` and load skills on demand.

**Shared policy in one place**: `AGENTS.md` holds the rules that apply to everyone (quiz budget, logging, prompt rules). Each agent file opens by deferring to it, so a policy changes in one file only.

**Phases**: Agents and skills are released incrementally (`PHASE.md`). An agent file may be present but not yet "live". Check the "Available from" column in `AGENTS.md`.

**Logs as shared state**: Subagents cannot see each other's context, so cross-agent state (quiz budget, exercises, goals) lives in `teacher-log.jsonl` and `learning-log.jsonl` at the root, keyed by a `session` ID.

**Per-assignment files**: `@assignment analyze` creates one tracked `<NAME>.md` per assignment (for example, `PM1.2.md`), linked by `builds_on:`. Later `verify` and `submit` steps read from that file.

## Common gotchas
- **`.opencode/` → `.claude/` migration is in progress.** The working tree has deleted `.opencode/` and added an untracked `.claude/`, but 13 files under `.claude/` still reference `.opencode/...` paths (for example, `submit-package.sh` usage text and `assignment.md` → `.opencode/scripts/assign-source.sh`). The plugin `.claude/plugins/learning-opportunity.ts` is an opencode plugin and is not loaded by Claude Code.
- **Doc and file name drift.** `README.md` links `PHASES.md`, but the file is `PHASE.md`. `PHASE.md` says "baseline (2 of 3)" while listing phase-2 agents.
- **Hook installation.** `setup.sh` calls `hooks/setup-git-hooks.sh`, which the comment in `baker.yml` says copies the wrong files. `baker.yml` installs `hooks/pre-commit` directly instead. `hooks/post-commit` fires only in a real terminal (`[ -t 0 ]`) and only if `opencode` is on PATH.

## Suggested exercise sequence
1. **Open `AGENTS.md` and read the "Delegating to subagents" table and the "Agent contract" section.** Then close it and explain, in your own words, how this repo keeps eight different agents from stepping on each other's jobs. Name the two mechanisms involved (role delegation and frontmatter permissions) and why the shared rules live in this file and not in each agent.

2. **Open `.claude/plugins/learning-opportunity.ts` and read its header comment (the first ~20 lines), then `hooks/post-commit`'s header comment.** Then explain: what event triggers a learning-opportunity offer, why there are two separate mechanisms for it (inside vs. outside opencode), and what they share so that a student isn't offered too many exercises.
